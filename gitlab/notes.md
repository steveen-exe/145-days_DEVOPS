# GitLab CI/CD Practice Notes: Variables, Secrets & Artifacts

## Module 1: Variables & Secrets

### 1. Core Definitions
* **CI/CD Variables:** Key-value pairs used to configure pipeline environments, inject application configurations, or pass credentials without hardcoding them into source repositories.
* **Environment Variables:** Dynamic values accessible to shells and processes running inside GitLab Runner execution environments.

### 2. Variable Scopes (Project vs. Group)
* **Project Variables:** Configured under *Project Settings > CI/CD > Variables*. Access is isolated exclusively to pipelines running within that individual project.
* **Group Variables:** Configured under *Group Settings > CI/CD > Variables*. Automatically inherited by all downstream subgroups and repositories, making them ideal for organizational or team-wide credentials.

### 3. Security Settings (Protected vs. Masked)
* **Protected Variables:** Injected only into jobs executing on protected branches (e.g., `main`, `production`) or protected tags. This mitigates the risk of rogue feature branches or pull requests stealing production secrets.
* **Masked Variables:** Automatically replaced with `[MASKED]` in the pipeline job logs if accidentally printed via standard output (`echo`). Value syntax must conform to specific rules (e.g., no spaces, minimum length) to enforce masking.

### 4. Direct Evaluation & Syntax inside `.gitlab-ci.yml`
* **Interpolation:** Variables are evaluated at runtime using `$VARIABLE_NAME` or `${VARIABLE_NAME}` syntaxes.
* **Conditional Logic:** Leveraged within `rules:if` clauses to control job execution:
  ```yaml
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
  ```

## Module 2: Artifacts & Test Reports (Artifactry Practice)

### 1. Basic Build Artifacts
Artifacts are files or directories generated by a job that are uploaded to GitLab and can be downloaded via the UI or passed to subsequent pipeline stages. They automatically expire after a defined duration.

```yaml
build_app:
  stage: build
  script:
    - npm run build
  artifacts:
    paths:
      - dist/
      - bin/
    expire_in: 1 week
```

### 2. Passing Variables via `dotenv` Reports
When variables are dynamically computed *during* job runtime, standard `variables:` declarations cannot capture them. A `.env` file passed via `artifacts:reports:dotenv` exposes these variables to all downstream stages natively.

```yaml
generate_meta:
  stage: build
  script:
    - echo "APP_VERSION=v2.6.$CI_PIPELINE_IID" >> build.env
  artifacts:
    reports:
      dotenv: build.env

deploy_app:
  stage: deploy
  script:
    - echo "Deploying target version $APP_VERSION"
```

### 3. Automated Test & Coverage Reports
Integrating test outputs natively into the GitLab Merge Request (MR) interface requires parsing specific file patterns through the `artifacts:reports` primitive.

* **JUnit XML Reports:** Exposes test summaries (success/failure rates) right within the MR widget.
* **Cobertura/Jacoco XML Reports:** Visualizes code coverage deltas within the changed lines of code inside the MR.

```yaml
run_tests:
  stage: test
  script:
    - npm run test -- --reporter=junit --output=reports/junit.xml
    - npm run coverage -- --format=cobertura --output=reports/cobertura.xml
  artifacts:
    reports:
      junit: reports/junit.xml
      coverage_report:
        coverage_format: cobertura
        path: reports/cobertura.xml
```

## 🚀 Scenario Practice Answers

### Scenario 1: AWS Credentials across 5 Team Repositories
* **Placement:** Define the AWS keys as **Group Variables** so all 5 repositories inherit them automatically.
* **Security Flags:** Turn **ON** both **Protected** (so keys are only exposed to deployment/production branches) and **Masked** (to hide keys if accidentally printed in logs).

### Scenario 2: Dynamic Deployment URLs
* **Strategy:** Use an `artifacts:reports:dotenv` configuration. Write the generated staging environment URL to a file in the provisioning job, and it will be readily available as a standard environment variable in the testing/verification job.
